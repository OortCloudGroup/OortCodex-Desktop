## 修复 macOS（zsh + npm）上的两个安装失败

用户在 macOS（/Users/lanjian，zsh）执行远程一键安装，遇到两个问题：

### 1. zsh 报 `BASH_SOURCE[0]：未绑定的变量`

- `install-cli.sh` 里 `SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"` 在 zsh 下
  `BASH_SOURCE` 不存在，配合 `set -u` 直接报未绑定变量。
- 修复：先用 `$0` 兜底，再在 `if [ -n "${BASH_SOURCE:-}" ]` 中覆盖为 `${BASH_SOURCE[0]}`
  （不能用 `[ -n ... ] && ...` 短路写法：在 `set -e` 下有提前退出风险）。
- 验证：`bash -n` 通过；文件模式与 `cat | bash` 管道模式均正常自举下载 mjs，无该报错。

### 2. `npm install -g` 报 EACCES（退出码 243）

- 原因：曾用 sudo 跑过 npm，`~/.npm/_cacache/index-v5` 下留下 root 属主文件，
  普通用户写入被拒（errno -13）。npm 自己给出的修复是 `sudo chown -R 501:20 ~/.npm`。
- 修复（`install-cli.mjs`）：
  - 新增 `isDirWritable`（权限位 + 实际 mkdir 探测，父目录可写不代表能写进去）、
    `isOwnedByUser`（statSync().uid !== process.getuid() 即视为不可用；Windows 无 getuid 则跳过）、
    `isCacheUsable`（依次检查 cache 根、`_cacache`、`_cacache/index-v5`）。
  - `resolveCacheDir`：默认缓存不可用时自动改用 `~/.npm-oortcodex-cache`，**无需 sudo**；
    新增 `--cache <目录>` 参数与 `OORTCODEX_NPM_CACHE` 环境变量覆盖。
  - 安装前检查 `npm config get prefix`（含 lib/node_modules）可写性，不可写先打印修复指引；
    失败后按平台输出具体 chown 命令（Windows 提示管理员终端）。
- 单元测试（临时脚本 `%TEMP%\oort-cache-test.mjs`）：属主一致→true、属主不一致→false（触发回退）、
  无 getuid（Windows）→true、目录不存在→true，四种情况均符合预期。
- 未能端到端验证真实 npm 安装：沙箱 `spawnSync` 仍一律 EBUSY（`node --version` 子进程都起不来）。

## 修复 `irm | iex` 反复报「赋值表达式无效」：`param()` 移除

- 现象：用户执行 `$env:OORTCODEX_CLI_VERSION='0.0.2'; irm .../install-cli.ps1 | iex`
  持续报 `无效赋值表达式 / InvalidLeftHandSide`。
- 定位：拉取远程文件比对字节 —— 远程 ps1 仍是 **7552 字节、带 BOM（ef bb bf）**，
  本地新版 **9224（现 11170）字节、无 BOM**。同时发现远程 `install-cli.mjs`（12105 vs 16389）
  与 `install-cli.sh`（5650 vs 5964）也都是旧版，只有 `.bat` 一致 → **用户尚未重新上传**。
- 根治（`install-cli.ps1` 重写）：**去掉 `param()` 块，改为手工解析 `$args`**。
  - 原因：带 BOM 时 BOM 被解码成 3 个可见字符顶在 `param` 前，`param()` 失去「首条语句」位置，
    整个脚本解析失败；去掉 `param()` 后这 3 个字符只被当成未知命令，报一行错后继续执行。
  - 手工解析支持 `-Version x`、`--version=x`、`-Version=x` 三种写法，并兼容 `--version=0.0.2`
    这种内联等号形式；未知参数只打印一行提示不中断。
  - 同步新增 `-Cache` / `--cache` 与 `OORTCODEX_NPM_CACHE` 透传给核心脚本。
- 验证（用「把 ï»¿ 按 UTF-8 无 BOM 写进文件开头」来等价模拟 irm 的 BOM 损坏场景）：
  - 带 BOM 版本：第 1 行报「无法识别…」后**继续执行**，成功下载 mjs 并跑完（npm 探测失败 exit 1）。
  - 干净版本：`-Version 0.0.2` 与 `--version=0.0.3` 均正确解析；版本不匹配 exit 1。
  - ps1 仍保持纯 ASCII（非 ASCII 字节 0）、无 BOM（head `23 20 6f`），latin1 / UTF-8 / 带 BOM 三种解码均可解析。
- 沙箱限制补充：PowerShell 工具对 `iex`、`& $scriptblock`、`.Invoke()` 这类动态执行会拦截；
  改用「写文件 + `powershell -File`」即可正常验证。

## 三个入口脚本回归测试：发现并修复 2 个 bug

### bug 1：`printNodeGuide` 版本号写死

- 现象：`--node-version 22.22.2` 时提示「请先安装 Node.js 22.22.2」，
  但下面命令却是 `winget install OpenJS.NodeJS --version 24.14.0`（写死成默认值）。
- 修复：`install-cli.mjs` 的 `printNodeGuide(requiredVersion)` 全部改用模板串取 `requiredVersion`
  （win32 winget/nvm-windows/msi、darwin nvm/pkg、linux nvm/nodejs.org 三分支都改）。
- 复测：指引与要求版本一致 ✅

### bug 2：sh 在 gte 模式下会误降级 Node

- 现象：`ensure_node_version()` 只做字符串相等比较，不管模式；
  `--allow-newer-node` 且当前版本更高时仍执行 `nvm use/install <要求版本>` → 把 24 降到 22。
- 修复：`install-cli.sh`
  - 新增 `NODE_MODE="${OORTCODEX_NODE_MODE:-exact}"`，并在参数循环里解析
    `--allow-newer-node`（→gte）、`--node-mode <值>`、`--node-mode=<值>`（同时仍透传给 mjs）。
  - `ensure_node_version()` 在 gte 模式下先用 `node -e` 比较版本，
    当前 >= 要求则打印「无需切换」直接返回，不再碰 nvm；exact 模式维持原行为。
  - 版本比较借 node 自身实现，避免在 bash/zsh 之间踩 `read -ra` / 数组语法差异。
- 复测：gte 不降级、exact 仍尝试切换、`OORTCODEX_NODE_MODE=gte` 环境变量生效 ✅
